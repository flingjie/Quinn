# Quinn 经历复盘与问题发现实施计划

日期：2026-09-24  
状态：待实施；依据《Quinn 实现方案 v3：以理解变化为核心的跨领域探索》和《Quinn 周期性回看开发实施计划》。尚未核查 Quinn 仓库；本文路径和字段是逻辑建议，不能视为已存在的实现。

## 1. 目标与设计判断

借鉴山田智惠《复盘自己：从记录到蜕变的行动指南》中的如实记录、聚焦、联结、视角切换，以及在抽象和具体之间往返的做法，为 Quinn 增加一个入口：**从真实经历中发现值得进一步探索的问题**。

Quinn 原有主线保持为「困惑或材料 → 不同解释与必要研究 → 新理解或开放问题 → 保存与回访」。新入口接在主线之前：「经历 → 观察与感受 → 候选线索 → 用户确认 → 原有探索主线」。周期性回看沿用现有方案，在有足够记录且用户主动要求时，对多个经历或讨论寻找可追溯的联系。

这个功能成功时，用户能从一件具体经历中辨认一个自己关心但尚未讲清的问题；或者在若干次记录后看清一条此前未注意到、同时经得起反例检查的线索。允许结果为“暂时没发现模式”“只是偶然事件”或“原来的理解仍成立”。

### 首版边界

- 不增加第四个 Skill，不新建每日打卡、习惯追踪、人生目标管理、人格画像或单独数据库。
- 不要求用户每天记录；不自动读取 Quinn 之外的日记、Finch 记录或私人资料。用户提供材料时才处理。
- 不从几次经历推断稳定特质、隐藏动机或心理状态；关于感受和意义，用户原话优先。
- 不把《复盘自己》的七种技巧做成每次必走的七步。只按卡点选用一个有帮助的动作。
- 不将 Quinn 的候选解释、行动建议写成用户已经接受的判断。
- 本计划与周期性回看计划互补：该计划负责跨期回顾，本计划补齐单次经历的入口与跨记录线索识别规则；相同的记录、归属和回访逻辑只实现一次。

## 2. 与 Quinn 现有设计的对接

| 组件 | 新增职责 | 边界与复用 |
| --- | --- | --- |
| `quinn-explore` | 用户讲述具体经历时，帮助区分事件、感受和解释；提出最多一两条候选线索，必要时切换视角；共同形成值得探索的问题 | 复用 v3 的框架转换、反例和现实检验；不自动挑战情绪或强求成长结论 |
| `quinn-synthesize` | 保存单次经历的阶段收获；用户要求回看时，跨相关记录寻找联系与反例 | 复用周期性回看中的检索、来源归属、纠正和继续位置；不默认为用户制定目标 |
| `quinn-research` | 当候选解释包含需查证的外部事实或机制时，按需查证 | 个人感受不需要外部证据来“证实”；不为了复盘而例行搜索 |
| 会话与记录工作区 | 将经历、用户原话、候选解释、确认结果、来源引用和回访条件关联 | 先核查 v3 的会话模型是否已实现；优先复用现有记录类型与原子写入机制 |

三个 Skill 的名称与职责来自 v3 **设计方案**，不代表仓库当前已有对应代码。若某部分未实现，依赖其最小能力落地，避免为复盘另起平行存储或流程。

## 3. 用户入口与交互

### 3.1 触发语义

- “今天和一个 Builder 聊完，我有点兴奋，但不知道为什么。”
- “我最近几次都在改 Finch 的定位，帮我看看在意的到底是什么。”
- “回看这一个月的讨论，有没有反复出现却没讲透的问题？”
- “我只想把这件事记下来。”

用户只要求记录时，记录事实和用户自述即可，不发起追问或长篇分析。用户要求探索时进入单次流程；要求比较过去记录时沿用 `quinn-synthesize` 的周期回看。没有足够资料时说明范围与缺口。

### 3.2 单次经历的最小流程

1. **复述观察**：区分「实际发生了什么」「用户说自己有什么感受或反应」「用户已经给出的解释」。缺失项留空，不补写内心活动。
2. **选择一个切入动作**：事件混杂则切分；表述含混则具体化；有明显张力则比较两种解释；用户已有清楚的解释则直接记录。每轮只选一个最有帮助的动作。
3. **给候选线索**：用「我看到的可能联系是……」表达，指出依赖的用户原话，以及还可能有哪些其他解释。没有线索时坦白说明。
4. **请用户校正关键点**：只有归属或意义会改变结论时问一个问题，例如“你更在意问题本身，还是这次交流让你看见了实际使用者？”用户可以否认、修改、跳过。
5. **形成出口**：保存用户明确确认的关注点；可选生成一个开放问题或最小观察行动。用户未确认时保存为 Quinn 的候选解释。

自然回复通常控制在两三段。避免依次展示“事件、情绪、意义、行动”的表格问卷；这些是 Quinn 的内部检查项。对强烈负面经历，先尊重用户叙述，不急于“重塑积极意义”。

### 3.3 跨记录发现线索

按用户指定范围或现有周期回看默认范围，先筛选候选记录，再读取完整相关内容；检索摘要不能直接当证据。通常只展示一两条最有意义的联系，每条包含：

- 涉及哪些具体经历或讨论，分别发生在何时；
- 重复的**可观察内容**是什么，用户先前有哪些解释；
- 是否存在反例、不同情境或记录不足；
- Quinn 的候选解释是什么，用户是否认可；
- 若值得继续，下一次应留意哪种信号。

“相同主题出现多次”不等于用户重视它，“相似的感受”也不等于同一原因。跨记录联结必须解释共同机制或问题，并容许用户指出只是表面相似。

## 4. 记录与归属契约

优先在 v3 的 `workspace/sessions` / `workspace/discussions` 中保存经历片段；实现前根据仓库实际模型确定是扩展现有文件，还是使用标注类型的普通 Markdown 记录。不要重复建设周期性回看的 `review` 类型。

一条经历在逻辑上需要以下内容；字段名以现有模型为准：

| 内容 | 约束 |
| --- | --- |
| `id`、`occurred_at`、`recorded_at`、`source_ref` | 事件日期未知时可空，不能把记录时间假装成事件时间；标出来源是当前叙述还是已有会话 |
| `event` | 用户描述的事件；概括时保留原文引用或可回溯位置 |
| `user_reaction`、`user_interpretation` | 只存用户明确表达；不由模型填充默认感受或价值观 |
| `candidate_pattern` | Quinn 的候选联系、依据、替代解释及不确定性 |
| `user_response` | confirmed / revised / rejected / unexpressed；附用户原话，不把沉默当确认 |
| `open_question`、`revisit_when` | 可选；行动与回访条件均不自动升级为已承诺目标 |
| `related_record_ids` | 指向完整记录的稳定 ID；允许同一经历后来用于多个主题回看 |

保持 v3 的版本检查、原子写入、引用有效性和失败告知。用户否认 Quinn 的解释时，保留原候选及否认的版本轨迹，更新当前摘要；绝不改写用户原始叙述。重复触发同一会话时优先继续或更新，不制造相同经历的多个“定论”。

如果现有记录无法区分用户原话与模型整理，应先加来源归属的最小字段及迁移读取规则；旧记录缺少明确归属时保持未知，不反推用户观点。

## 5. 分阶段实施

### P0：核查仓库及依赖

- [ ] 阅读仓库 `AGENTS.md`、三个 Skill 的实际入口、工作区记录格式、现有保存/恢复脚本和测试。
- [ ] 对照 v3 与周期性回看计划，列出已实现、部分实现、未实现功能；特别核查跨记录检索、用户原话归属、引用、纠正与版本冲突。
- [ ] 用用户允许的一至两段真实讨论作基线：一次单次经历，一次跨记录回看；记录当前交互的阻力和缺口。
- [ ] 输出实际文件改动清单，并决定经历片段落在现有哪类记录中。若周期回看 P0/P1 尚未实现，只建立双方共用的最低依赖。

验收：每项改动可映射到现有文件；明确哪些设计能力尚不存在；没有为新功能复制一套存储。

### P1：单次经历 MVP

- [ ] 在 `quinn-explore` 的触发说明加入“从经历发现问题”，实现事件、用户反应、解释的区分及一个切入动作。
- [ ] 在 `quinn-synthesize` 或现有会话保存环节落盘：保留原话、Quinn 候选、用户反馈和暂停位置。
- [ ] 增加两个自然语言出口：“只记录”和“继续探索”；默认不以固定问卷逼迫用户回答。
- [ ] 加入候选解释的归属约束，用户反对或跳过时正确保留其状态。

验收：输入一件真实经历后，Quinn 能用简短自然的对话提出一个值得探究的问题；用户否认推断后，不会将其保存为用户立场；只要求记录时不转成目标规划。

### P2：周期回看中的线索识别

- [ ] 复用《Quinn 周期性回看开发实施计划》的时间/主题检索与完整会话读取，不另建相似索引。
- [ ] 在 `quinn-synthesize` 的周期回看中加入“可观察重复 → 可能联结 → 反例/缺口 → 用户纠正”的分析顺序。
- [ ] 从抽象线索回到一项具体观察：下次什么经历会支持或削弱这个解释；没有合适观察点时保留开放问题。
- [ ] 将用户确认与 Quinn 候选区分写入同一回看记录，保留关联经历的原始 ID。

验收：对若干条相关记录能提出至多两条带引用的候选线索；一条表面相似却机制不同的记录不能被强行并入；记录稀疏时不编造“长期模式”。

### P3：真实试用与减负

- [ ] 用一次关于 Quinn 或 Finch 的真实项目取舍试用单次入口；隔一段时间用新材料试用回看。
- [ ] 检查 Quinn 的候选问题是否帮助用户说清真实关注点，用户纠正是否被吸收，是否过早引入心理化解释。
- [ ] 删除无助于判断的固定问题或字段；如多次试用都无需专门入口，保留为 `quinn-explore` 的一段轻量指引。

验收：用户能指出至少一条以前没讲清、且有具体经历依据的问题；或通过反例准确否定一条 Quinn 的解释。无需证明“人格成长”，也不以记录量作为成功指标。

## 6. 验收场景与必要验证

| 场景 | 正确行为 |
| --- | --- |
| 用户说“记下今天的讨论” | 保存叙述与来源，不强制分析或追问 |
| 用户说“这次交流让我很兴奋” | 将兴奋归于用户自述；原因仍为待确认假设 |
| Quinn 推测“你害怕公开表达”，用户否认 | 不写成用户特质，保留纠正并修订候选 |
| 两次改变 Finch 定位，但原因不同 | 标出差异，不因为主题相同就推导稳定模式 |
| 三个月只有一条可用记录 | 只回看这条记录，明确不能归纳长期趋势 |
| 新事实推翻先前归纳 | 保留原记录和修订轨迹，更新当前理解 |
| 用户只想讨论，不想行动 | 可以停在新问题或更准确的解释，不制造行动承诺 |
| 保存中断或并发更新 | 不覆盖用户原话，失败可见并能从原会话恢复 |

代码验证只覆盖具体风险：来源归属、引用完整、重复记录、版本冲突和恢复。认知表现使用真实且允许使用的样本人工检查：线索是否有依据、反例是否被考虑、问题是否值得继续、交互是否自然。

## 7. 建议实施顺序与交付

先做 P0，再将 P1 作为独立可用的最小改动；P2 与既有周期性回看计划合并实施，共用检索、记录和纠正机制；P3 以真实使用决定是否继续扩展。若 v3 的基本会话记录尚未落地，先补齐它的最低能力，不并行实现两个不兼容的存储方案。

交付内容：实际仓库改动清单、更新后的 Skill 指引、必要的记录/校验调整、一个单次经历和一个周期回看的可重演示例、上述验收结果，以及用户可直接使用的触发示例。实施时才确认真实文件路径；本计划本身不声称功能已上线。
